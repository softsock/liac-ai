# M2 Luna via OMP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** Connect real GPT-6 Luna through OMP to observe completed turns and prepare semantic context epochs asynchronously while Nemotron remains responsive and recoverable.

**Architecture:** One Runtime owns SQLite, one visible Fast stream, and one serialized Deep worker/session. Deep receives immutable Journal evidence and returns strictly parsed proposals; Runtime commits decisions and cursor changes atomically. Prepare semantic epochs at 75% of the Fast input budget; preserve M1.5's deterministic fallback above 90% without awaiting Luna.

**Tech Stack:** Python 3.12+, asyncio, SQLite, existing HTTPX/Nemotron tokenizer, optional official `omp-rpc` Python SDK, installed OMP 18.12.6, stdlib unittest.

**Spec:** [Original M2 requirements](../specs/2026-11-12-m2-luna-requirements.md). This plan's defaults and narrower operation taxonomy below are proposed implementation decisions, pending user review.

## Review Focus

1. An unfinished or interleaved superseded turn at a batch boundary must not split a user's message from its terminal outcome (Task 1).
2. A crash between note/epoch decisions and acknowledgement must leave either the complete durable result or replayable input (Task 2).
3. SDK cancellation does not stop a Python thread: no replacement child or prompt may start until old work and process teardown are confirmed (Task 3).
4. A late summary must preserve newer exact turns; changed note/epoch dependencies must cause an audited rejection and fresh analysis (Tasks 2 and 4).
5. Valid-looking model JSON may contain invented source IDs, booleans as versions, duplicate keys, or instructions embedded in dialogue; reject malformed data and never promote quoted evidence to identity/tools (Tasks 1 and 3).

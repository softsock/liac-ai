Продовжуємо розробку `softsock/liac-ai` після завершеного M4.3.

**Мета – перетворити наявний PySide6 Runtime Inspector на Conversation Lab, у якому можна вести звичайну розмову з Liac, запускати багатогодинні автоматичні симуляції та в реальному часі спостерігати всі доступні процеси Fast, Luna і Runtime.**

Це інструмент для дослідження поведінки всієї системи, а не нова когнітивна підсистема.

## 2. Принцип повної прозорості

Будь-яка дія Fast, Luna або Runtime, яка впливає на розмову чи контекст, повинна бути доступна для інспекції.

Для кожного виклику Fast показуй:

- Модель, ідентифікатор виклику, причину запуску.
- Точний prompt, який відправляє наш adapter.
- Context Epoch, Markdown Context, історію та поточний input.
- Streaming output і його завершення.
- TTFT, кількість токенів, latency, доступні KV-cache counters.
- Cancellation, помилки та кінцевий статус.

Для кожного виклику Luna:

- Причину виклику й canonical event evidence.
- Повний доступний input, role prompt і OMP session context.
- Статуси `queued`, `analyzing`, `completed`, `failed` тощо.
- Сирий доступний результат і parsed proposal.
- Markdown update, compaction, initiative.
- Що Luna запропонувала і що Runtime фактично прийняв або відхилив.
- Причини відхилення, конфліктів, no-op та retry.
- Usage, latency, session ID і доступні provider metrics.

Для Runtime:

- Journal events.
- Context revisions та epoch switches.
- Зміни `context.md` у вигляді Markdown diff.
- Pending/claimed/cancelled initiative.
- Deep cursor, lag, активний Fast, черги та lifecycle.
- Restart, recovery, cancellation і compaction.

Всі пов'язані процеси повинні мати зрозумілі ідентифікатори, часові мітки й можливість переходу між ними.

**Важливо:** показуй усе, що реально доступне нашій системі. Не вигадуй приховані reasoning traces або точний provider-wire prompt, якщо OMP/SDK їх не надає. Такі дані позначай як unavailable.

## 3. Оновлення PySide6 Inspector

Збережи поточний PySide6 Widgets та існуючий RuntimeWorker.

Запропонована організація:

### Conversation

Основний чат, придатний для дуже довгих діалогів.

Візуально розрізняй:
- Реального користувача.
- Симульованого користувача.
- Звичайні відповіді Nemotron.
- Автономні репліки Liac.

Показуй streaming, паузи, cancellation і межі сесій.

Натискання на репліку відкриває пов'язані Fast/Luna процеси.

### Process Timeline

Жива хронологія всіх процесів.

Можна відфільтрувати Fast, Luna, Runtime, Context, Initiative та Simulator.

Кожна подія відкриває детальний Inspector.

Події повинні надходити під час роботи моделей, а не лише після завершення розмови.

### Inspector

Використай наявні вкладки, покращивши їхню організацію:

- Input / Prompt
- Output / Proposals
- Context / Diff
- Metrics
- Journal / Raw JSON

Особливо важливий **Context Timeline**: можливість вибрати момент розмови й побачити Markdown Context та Context Epoch саме на той час, а не їхній сьогоднішній стан.

### Simulation

Компактна панель керування:

- Сценарій.
- Кількість turns або тривалість.
- Start / Pause / Resume / Stop.
- Поточна фаза симуляції.
- Прогрес та витрати.
- Можливість ручного втручання.

Залиш інтерфейс зручним для ручної розмови. Не перетворюй його на перевантажений dashboard.

## 4. User Simulator

Створи окремий headless simulation runner, який використовує **справжній Liac Runtime** через його публічний API.

Simulator – це тестовий клієнт, а не частина когнітивної архітектури.

Для генерації повідомлень можна використовувати окрему frontier LLM через наявну інтеграцію OMP, але з незалежною сесією, інструкціями та історією. За необхідності додай мінімальний окремий adapter.

Simulator повинен імітувати людину, а не асистента, який намагається підтримувати діалог.

У нього є:

- Власна особистість та стиль спілкування.
- Повсякденні справи, інтереси, проблеми.
- Приховані факти й наміри.
- Причини змінювати теми.
- Можливість повернутися до старої розмови.
- Можливість замовкнути або завершити сесію.
- Іноді суперечливі чи неточні висловлювання, які пізніше виправляються.

**Simulator не отримує приховані думки, Markdown Context або внутрішні рішення Luna.** Він бачить лише те, що міг би бачити звичайний співрозмовник.

Сценарій задає життєву ситуацію та можливі події, але не прописує кожне повідомлення.

Не змушуй симулятор постійно ставити запитання.

## 5. Реалістична довга комунікація

Перший цільовий сценарій – 100–150 turns, розподілених на кілька умовних сесій.

Наприклад:

**Session 1 – Introduction**

Знайомство, інтереси, природні відхилення від теми.

**Session 2 – Ongoing Project**

Користувач займається Skin Creator, змінює плани, іноді жартує або скаржиться.

**Session 3 – Return**

Користувач повертається після перерви й побіжно згадує попередні події. Перевіряємо contextual continuity.

**Session 4 – Corrections & Pressure**

Змінюються старі факти, з'являються суперечності, відбувається compaction, Luna працює паралельно з Fast.

**Session 5 – Ordinary Conversation**

Розмова без спеціальної мети: паузи, короткі відповіді, нові теми, природне мовчання.

Це початковий сценарій, а не обов'язковий шаблон усіх симуляцій.

Передбач короткий smoke-run на 10–15 turns для перевірки інтеграції.

Підтримай реальні паузи та, де доречно, контрольований test clock для прискорення перевірок часу. Не підробляй час у production Journal і не заявляй, що прискорена симуляція еквівалентна кільком годинам реального виконання.

Використовуй окрему SQLite-базу для кожного тестового прогону. Не зачіпай звичайні розмови користувача.

## 6. Initiative & Continuity

M4.3 має бути повністю доступним із PySide6 Lab.

Додай перемикач `Enable initiative`, вимкнений за замовчуванням.

В інтерфейсі показуй:

- Чому Luna запропонувала самостійну репліку.
- Коли вона стала допустимою.
- Чи була виконана.
- Чи її скасували.
- Чому Runtime відхилив пропозицію.
- Чи сформував Nemotron природну репліку.

Для Simulator принципово важливо не відповідати миттєво після кожного повідомлення Liac. Інакше автономна ініціатива ніколи не отримає природного простору.

Після деяких повідомлень симулятор повинен справді замовкати.

## 7. Дані, метрики та replay

Кожен прогін зберігай у локальному Git-ignored каталозі.

Зберігай:

- Transcript.
- Всі доступні Fast/Luna trace events.
- Simulator prompts, responses і рішення щодо пауз.
- Context revisions, Markdown diffs, epochs.
- Runtime metrics.
- Налаштування сценарію, моделі, версії коду та seed, якщо використовується.

Replay означає **відтворення записаної історії для перегляду**, а не повторний inference з гарантією ідентичних відповідей.

Після завершення симуляції я повинен мати змогу відкрити її в PySide6, знайти конкретний turn та побачити всю пов'язану активність Fast, Luna і Runtime.

Не записуй API credentials або приховані provider reasoning data. Зберігай обмеження на розмір capture, показуй пропущені дані й не блокуй inference повільним записом.

## 8. Оцінювання

Додай компактний підсумок прогону:

**Технічні показники:**
- Загальні turns і Deep calls.
- TTFT p50/p95.
- Token usage і доступні KV-cache counters.
- Кількість compactions.
- Deep lag.
- Errors, failed proposals, cancellation.
- Ініціативи: proposed / spoken / cancelled / expired.

**Поведінкові показники:**
- Збереження важливих фактів.
- Реакція на виправлення.
- Повторення реплік і жартів.
- Надмірні запитання.
- Assistant-like behavior.
- Доречність ініціатив.
- Зв'язність характеру.

Поведінкові оцінки можна отримувати від незалежної LLM після завершення прогону. Вона повинна бачити діалог та цільові критерії, а не приховані міркування Luna. Її висновки – суб'єктивні оцінки з прикладами, не доказ правильності.

Коли сценарій має перевірювані факти, використовуй їх як окремі об'єктивні критерії.

Не створюй великий універсальний evaluation framework.

## 9. Архітектурні обмеження

- Headless Runtime залишається незалежним від PySide6.
- Симулятор і ручний чат використовують той самий Runtime.
- Немає другого Journal чи альтернативного контексту Liac.
- Окремий Simulator не має доступу до прихованого стану Liac.
- Всі Qt-оновлення проходять через безпечну межу worker/UI.
- Немає блокування Fast через trace capture.
- Немає змін характеру Nemotron чи Luna тільки для проходження тестів.
- Поточні Context Epochs, Markdown, cancellation, initiative і KV cache залишаються незмінними за семантикою.

Розумно обмежуй обсяг змін і автоматизованих тестів. Перевір критичні lifecycle/concurrency інваріанти й надай пріоритет реальному end-to-end запуску.

## 10. Практична перевірка

Використай реальний Nemotron через LM Studio й Luna через OMP.

Спочатку перевір наявні endpoints, модель і tokenizer; не завантажуй нових моделей та не змінюй загальні налаштування LM Studio.

Послідовність:

1. Ручна розмова в оновленому Inspector: повне Fast/Luna трасування.
2. Smoke simulation на 10–15 turns.
3. Реальна довга симуляція на 100–150 turns, якщо провайдери доступні й коротка перевірка успішна.
4. Відкрити збережений прогін і перевірити зв'язок між репліками, процесами, контекстом і метриками.
5. Перевірити ініціативу, silence, correction, compaction, restart і Fast/Deep concurrency.

Не маскуй невдалі або неприродні діалоги. Збережи їх як evidence.

Якщо повна довга симуляція не завершиться, зафіксуй фактичний прогрес і причину, не заявляючи про успішне проходження.

## Definition of Done

Я можу запустити PySide6 Conversation Lab, вручну поспілкуватися з Liac або запустити довгу LLM-симуляцію.

Під час виконання я бачу **кожен доступний процес Fast, Luna, Runtime та Simulator**, їхні inputs, outputs, рішення й зміни контексту.

Після завершення можу відкрити історію, вибрати довільну репліку й дослідити, як система дійшла до неї.

Головний результат M4.4 – **можливість реально досліджувати довготривалу поведінку Liac**, а не просто отримати ще один набір зелених тестів.
